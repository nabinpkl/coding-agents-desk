# TASKS: v0 media-output friction (with R25 datagram media captured)

`R<N>` = remaining. `D<N>` = done. Numbers are stable; retire dropped IDs in the promotion log, never reuse.

Archived history: `tasks/archive/2026-06-16-v0-space-agent-host-overlay.md` carries the closed v0 work through Space Agent plus the first R24 capture.

## Position

The active v0 problem is no longer "can input reach the Mac." Input is smooth. The friction is that the iPhone video output trails during scroll and other high-motion desktop changes.

The next direction is to keep dual-plane WebRTC as the measured baseline while testing the single-surface owned media path from ADR-0013. More sender knobs did not preserve both constraints at once, the HEVC-through-`stasel/WebRTC` path exposed package and platform-wrapper risk rather than a clean codec upgrade, and the first owned WebSocket media path reproduced a classic TCP video failure: during scroll the host kept accepting input while the client video froze and then drained late frames seconds later. The working order is:

- Keep two warm video planes in one PeerConnection: a full-resolution VP9 detail plane for rest-state text and a capture-downscaled H.264 motion plane for scroll.
- Switch the client compositor to motion immediately on scroll touch-down.
- Restore the detail plane only after a fresh detail frame renders, so at-rest text returns crisp instead of showing the stale or downscaled motion plane.
- Treat WebRTC as the baseline to beat, not the strategic media primitive.
- Test the owned encoded-video prototype only across the contested surface: ScreenCaptureKit frame scheduling, VideoToolbox encode/decode, datagram pacing, receiver buffering, feedback, and client render timing.
- Reuse pairing, session authentication, Tailscale-only networking, the dedicated input WebSocket, Keychain credentials, existing config, and the `VideoFrameSink` / `MediaTransport` seams.
- Do not reintroduce dual rest/motion planes or TCP/WebSocket video in the owned path. Owned mode has one detail surface and discards stale video at the datagram layer.
- Escalate to RDP-style mixed graphics only after owned full-frame hardware video over QUIC datagrams proves which text and scroll problems remain.

This file is now the active R24 ledger. Closed v0 feature history stays in the archive unless a past decision needs to be referenced.

## v0 Phase 12 (R24): media-output friction and architecture direction

Phase goal: preserve the native-feeling input path while making video output keep up during scroll and cursor-heavy daily-driver use.

What is already on `main`: the cursor path has local prediction, host cursor-position seeding, host held-position integration, and host-driven cursor glyph mirroring. The scroll path sends an interaction hint on scroll-strip touch-down, uses a steeper client scroll curve, and now drives a client compositor that switches between hot detail and motion video planes.

H.264-only runs exclude VP8 and VP9 fallbacks, and host / client stats log a mismatch if the RTP codec escapes the configured set.
- [x] D24.12. H.264 hardware encoder guardrail. The first strict H.264 run connected and selected `video/H264` with `encoder=VideoToolbox`, but outbound RTP stayed black because `framesEncoded=0` and `bytesSent=0` while capture frames kept arriving at 3600x2338. `host/AgentDeskHost/MediaTransport.swift` now derives H.264-only sender guardrails that disable VP9-style temporal layering and use `maintainFramerate`. `host/AgentDeskHost/ScreenCaptureKitFrameSource.swift`, `host/AgentDeskHost/VideoFrameSource.swift`, and `host/AgentDeskHost/MediaStack.swift` downscale the ScreenCaptureKit output before frames enter WebRTC, because sender `scaleResolutionDownBy` alone did not keep VideoToolbox from seeing the native-size frame. - [x] D24.13. H.264 post-scroll restore. The first non-black H.264 run restored from scroll to the same sender `scaleDown=3.5` used during scroll, so quality stayed in the low-resolution profile after the interaction ended. `host/AgentDeskHost/MediaTransport.swift` now keeps H.264 crisp sender scale at the base profile while leaving the hardware-safety downscale in the ScreenCaptureKit source, and `host/AgentDeskHost/LibWebRTCMediaTransport.swift` applies the crisp profile at sender startup so startup and post-scroll restore match.
- [x] D24.14. Hot dual-plane renderer. `MediaTransport.start` now carries `VideoPlaneSources` / `VideoPlaneSinks`. The host creates two warm WebRTC video tracks in one PeerConnection: `detail-video` uses VP9 at full ScreenCaptureKit resolution for rest-state text, and `motion-video` uses H.264 with capture-level downscale for low-latency scroll. The client receives both tracks into `DualPlaneVideoSink`, switches visible output to motion on scroll start, and switches back to detail only after a fresh detail frame render callback. The old host-side interaction hint no longer mutates one sender profile; it remains as a logged compatibility signal while the client compositor owns the visible plane.
- [x] D24.15. Motion-plane quality floor. The first dual-plane device feel pass showed scroll was smoother but motion output was too blurred to read. - [x] D24.17. Motion capture downscale tuning. The post-pass-through H.264 quality tests showed bitrate / FPS tuning still did not match the earlier VP9-like readable motion quality. `host/AgentDeskHost/MediaTransport.swift` now exposes `AGENTDESK_TUNING_MOTION_CAPTURE_SCALE_DOWN` for the H.264 motion plane capture scale while leaving the VP9 detail plane at full resolution and the motion sender scale at `1.0`. `host/AgentDeskHostTests/ScrollQualityTests.swift`, `.env.example`, and `SPEC.md` pin the new tuning surface.

It explicitly reuses ScreenCaptureKit, VideoToolbox, pairing, session authentication, Tailscale-only networking, the dedicated input channel, and existing protocol seams.

## v0 Phase 13 (R25): single-surface datagram media

Phase goal: remove TCP/WebSocket video from the owned media path, keep input/auth unchanged, and test whether one hardware HEVC detail surface over datagrams can beat WebRTC on scroll output without giving up crisp rest text.

R25 sub-tasks:

- [x] D25.1. Single-surface UDP owned media. ADR-0013 supersedes ADR-0012's proposed control map with the concrete rule: no dual rest/motion planes in owned mode, no TCP/WebSocket video, and no codebase defense where the old path is weak. `host/AgentDeskHost/OwnedMediaTransport.swift` now starts a UDP listener on the signaling port, validates the first-datagram `MediaChannelHello` through `SessionRegistry`, replies with `MediaChannelReady`, and derives an HMAC key from the media capability plus client/server nonces. `host/AgentDeskHost/OwnedMediaChannelServer.swift` packetizes `ADMF` envelopes into authenticated `ADMD` datagrams and stops stale frame sends when a newer frame arrives. `client/AgentDeskClient/OwnedMediaTransport.swift` opens UDP, performs the nonce handshake, reassembles only the newest complete frame, and feeds the single-surface sink. `client/AgentDeskClient/OwnedMediaVideoSink.swift` now owns one `AVSampleBufferDisplayLayer`; `SessionReady.mediaPlanes` advertises only `detail` for owned mode; `PairingSignalingServer` rejects `media-hello` as a WebSocket first frame. `just check` is green.
- [ ] R25.2. Device owned-UDP feel pass. Run the WebRTC baseline and the owned UDP prototype on the same physical iPhone scroll trace, capture codec, encode, decode, render cadence, visual scroll smoothness, and rest-state text crispness. Start with `AGENTDESK_MEDIA_STACK=owned AGENTDESK_OWNED_MEDIA_CODEC=hevc AGENTDESK_OWNED_MEDIA_CHROMA=444 AGENTDESK_OWNED_MEDIA_HEVC_PROFILE=main444 AGENTDESK_OWNED_MEDIA_MAX_QP=24 just fresh-install`; compare default 4:2:0 HEVC and `AGENTDESK_OWNED_MEDIA_CHROMA=bgra` only after the strict ceiling path is felt. First black-output run was not a decoder failure: UDP instrumentation showed every `ADMD` packet failed length validation because the decoder treated the header as 30 bytes and read `payloadLength` from byte 28 inside `sentAtUptimeNs`; the fixed wire shape is 32-byte header, 32-byte HMAC, payload length at byte 30. The next physical run proved the host was sending continuous keyframes and deltas, and the client was showing video, but the output trailed badly. The current probe treats `AVSampleBufferDisplayLayer` as an immediate-display remote-desktop surface by removing host presentation timestamps before enqueue and flushing queued display history only on keyframes or layer failure. Simulator use was not comparably laggy, which points away from generic display-layer backlog and toward physical-device packet pressure. Owned mode now exposes capture scale, bitrate, FPS, and keyframe interval knobs to test that directly. The reduced-pressure device run still froze under repeated up/down scroll even though the earlier TCP 4:2:0 path was workable. That rules out "make fewer packets" as the architecture fix and points at the missing UDP media recovery layer: incomplete frames are abandoned, delta frames depend on prior decode state, keyframes are large and lossy, and there is no ACK/NACK, FEC, retransmit, congestion response, or immediate keyframe-request feedback.
- [x] D25.3. QUIC datagram owned media. ADR-0014 supersedes the raw UDP carrier from ADR-0013 without changing the single-surface rule: no dual rest/motion plane and no TCP/WebSocket video. `host/AgentDeskHost/OwnedMediaTransport.swift` starts a QUIC datagram listener on the signaling UDP port with the existing Tailscale TLS identity and media capability validation. `client/AgentDeskClient/OwnedMediaTransport.swift` opens a QUIC datagram connection, keeps the `MediaChannelHello` / `MediaChannelReady` nonce handshake, requests a keyframe when it abandons an incomplete frame, and drops post-loss deltas until a keyframe arrives. `host/AgentDeskHost/OwnedMediaChannelServer.swift` receives `OwnedMediaControlMessage(kind=keyframe-request)` and `VideoToolboxOwnedMediaEncoder` forces the next encoded frame to be a keyframe. `just check` is green.
- [x] D25.4. TestFlight archive prep. `client/AgentDeskClient/Assets.xcassets`, `client/AgentDeskClient.xcodeproj/project.pbxproj`, `client/AgentDeskClient/Info.plist`, and `Justfile` add opaque iOS app icons, wire `AppIcon` into the client target, move version/build numbers to `MARKETING_VERSION` and `CURRENT_PROJECT_VERSION`, and add `client-archive` plus `client-open-archive` recipes. `just check` is green and `just client-archive` creates `/tmp/AgentDeskClient.xcarchive`. The local archive is still signed with the installed Apple Development identity; TestFlight upload remains a human external action in Xcode Organizer until an Apple Distribution identity or cloud-managed distribution signing is available.
- [x] D25.5. QUIC recovery storm guard. The first Wi-Fi physical run after TestFlight setup reproduced the owned-media failure as a protocol recovery loop: stale queued frames became fresh as the send gate drained them, the client requested a keyframe for every abandoned incomplete frame, and the host preserved every requested keyframe. `host/AgentDeskHost/OwnedMediaChannelServer.swift` now uses the encoder frame id at enqueue time and supersedes old keyframes with newer keyframes; `client/AgentDeskClient/OwnedMediaTransport.swift` now debounces keyframe requests while it is already waiting for recovery. `host/AgentDeskHost/SharedTypes.swift`, `client/AgentDeskClient/SharedTypes.swift`, `host/AgentDeskHostTests/ScrollQualityTests.swift`, and `client/AgentDeskClientTests/InputChannelTests.swift` pin the send-freshness and request-throttle contracts. `just check` is green. The follow-up strict 4:4:4 physical run no longer produced a same-millisecond request flood, but it still sent roughly 500 datagrams per keyframe and kept entering recovery. The default 4:2:0 HEVC physical run cut keyframes to roughly 150 to 173 datagrams, but still entered recovery repeatedly under scroll, so packet count improved but the datagram-only recovery model still needs either lower capture pressure or a stronger recovery / pacing layer before it can beat WebRTC on motion.

## Alternatives and Direction

| Option | Direction | What it catches | Failure shape | Gate |
| ------ | --------- | --------------- | ------------- | ---- |
| Hot dual-plane WebRTC | Baseline to beat | Rest text stays on the full-resolution detail plane while scroll uses a capture-downscaled-only motion plane | Continuous dual encode can cost CPU, bandwidth, or receiver decode headroom | Keep only if R25.2 fails to beat it on the same trace |
| Keep tuned WebRTC and sender profiles | Superseded by D24.14 | Encoder / pacer pressure during scroll, without replacing the media stack | One plane could not keep scroll smooth and rest text crisp after H.264 downscale | Revisit only if dual-plane continuous cost is worse than switching cost |
| H.264 on both ends | Superseded as sole stream | Hardware decode on iPhone and simpler negotiation | At-rest text was unreadable after the quality reductions required for scroll | Keep as the motion plane while detail uses VP9 |
| VP9 with temporal layers | Superseded as sole stream | Screen-content compression and bitrate-layer shedding during scroll | Scroll remained visibly laggy despite rest-state crispness | Keep as the detail plane unless device stats prove decode is the bottleneck |
| Upgrade the WebRTC build | Rejected for current HEVC path | Hardware codec exposure, lower receiver-buffer controls, codec preference reality | `stasel/WebRTC` H265-era packages are not a clean macOS host dependency; a private WebRTC build would add build ownership without enough media control | Reopen only with a cleanly importing macOS+iOS WebRTC artifact that advertises `H265` at runtime |
| Owned VideoToolbox QUIC datagram media transport | Active R25 direction | Full ownership of frame pacing, receiver buffering, late-frame drop, codec lifecycle, and crisp detail surface while avoiding raw UDP congestion blindness | Still needs app-level loss recovery because QUIC datagrams do not retransmit media | R25.3 single-surface owned QUIC trace beats tuned WebRTC on the same device |
| Owned HEVC 4:4:4 ceiling probe | Active exploration | Whether chroma subsampling and high QP, not transport timing, explain the subtle text degradation versus VP9 | ScreenCaptureKit or iPhone decode may reject the strict path, or bandwidth may rise too far for motion | Use only to find the ceiling, then back down to the simplest stable owned path |
| RDP-style mixed graphics | Captured as later escalation | Separates text/detail refresh, scroll-copy, dirty regions, and motion video | Larger protocol surface and correctness burden | Revisit after owned full-frame hardware video proves which text and scroll gaps remain |
| Code-aware crisp-text overlay | Captured, not active | Separates text legibility from video codec quality | Adds a second rendering model and risks drifting from the real desktop | Revisit only after tile/detail refresh still fails steady-state text |

### Rejected For Now

- A direct transport overhaul before instrumentation. Rejected because the observed symptom can come from software decode, receiver buffering, or render scheduling. Revisit after R24.7.
- More aggressive scroll-profile tuning without codec verification. Rejected because the latest VP9 temporal-layer work may be inert if the client negotiates H.264. Revisit after R24.10.
- A cold second stream or negotiated stream replacement on scroll. Rejected because scroll needs an already-hot plane. D24.14 keeps both planes warm and pays the continuous cost deliberately.
- Full protocol replacement. Rejected because pairing, session auth, input, Keychain state, and Tailscale-only networking are not the failing pieces. ADR-0014 keeps those surfaces and owns only single-surface QUIC media timing, feedback, and encoded-frame movement.
